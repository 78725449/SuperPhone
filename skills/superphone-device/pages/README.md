# 页面签名（资产 L1 页面表的第一块）

> **这是【入库的资产】，不是运行时缓存** —— 与 `data/skill-cards/`（运行时产生、不入库）不同类。
> 采集与判定工具：`scripts/page.py`（`snapshot` / `which` / `verify` / `list`）。

## 它解决什么问题

一期跑「打开抖音搜南京美食」时暴露了三条约束（详见 `docs/known-issues/02-设备端与构建.md`）：

| 约束 | 现象 |
|---|---|
| `wait_for{hashDiff}` 热启动会超时 | App 已在后台且恢复上次页面时，`open` 是瞬时切换、画面不变 → 白等到超时并中止整条脚本 |
| `back`（边缘右滑）不是万能的 | 抖音搜索页不响应边缘右滑（连发两次，OCR 逐字相同）|
| **★ 缓存坐标需页面前置条件** | App 会恢复到上次离开的页面 → `tap{0.928,0.066}`（"首页的搜索图标"）在非首页会点到完全错误的东西 |

**三条的共同解 = 先回答「我在哪个页面」。**

---

## ★★★★ 实测结论（2026-09-19，先说结论再说格式）

| 页面 | 性质 | `verify` 结果 | 判断 |
|---|---|---|---|
| **搜索输入页(有键盘)** | **静态** | **最低 0.97 · 平均 0.99 · 5/5 通过** | **✓ 非常好用** |
| **首页** | **动态视频流** | **最低 0.20 · 平均 0.44 · 2/5 通过** | **✗ 不可用** |
| 跨页误判（首页 vs 搜索页）| — | **0.00** | **✓ 不误判** |

**★ 结论：本方案对【静态页】可靠，对【动态页】先天不足。**

**为什么动态页不行**：抖音首页的结构特征是**底部 tab（图标 + 小字）**，
而**图标类控件恰恰是 OCR 最不可靠的东西** —— 实测同一页面反复 OCR，
"消息 / 朋友 / §底部导航"时有时无（视频每帧内容也不同，pHash 五轮全不同）。

**→ 下一期的方向已经明确**：动态页要靠 **图标模板匹配**（`vision.find_image`，机制已有、缺素材库），
而不是继续在 OCR 上打磨。详见 `实施设计-…§资产四层` 的 L0 图标素材库。

## ★★★ 四个关键设计（都是实测逼出来的，不是设计的）

### 1. 必须【多次采样取高频】，不是取严格交集 —— 分离"结构"与"内容"

只采 1 次时签名会混入**内容**（点赞数 / 视频标题）。

**实测**：抖音首页采 1 次得 17 个词、其中 12 个是内容 →
**换一个视频后判定得分从 1.00 掉到 0.29**，直接判不出页面。

> **结构词每次都在、内容词每次不同 → 取高频即结构。★ 这个分离是【自动】的，无需人工标注。**

**★ 但下限不能是"N/N 全在"**：实测用严格交集只剩 3 个词，验证时 2 轮只剩 2/3 命中
（**OCR 会偶尔漏识某个词**）→ 余量太小；改成 `samples-1`（5 次取 ≥4、3 次取 ≥2）后余量正常。

### 2. 必须用【子串匹配】，不能用【精确相等】—— OCR 分块边界不稳定

**实测**：用"块字符串精确相等"求交集时得到**空交集（0 个共同文字）**，连"首页/朋友/消息"都没有。

**根因**：**OCR 的分块边界不稳定** —— 同一根顶部栏，
一次可能合成一块 `三 直播 团购 南京 关注 商城推荐`，另一次可能切成三块。

> **→ 一律在【去空白的大串】上做子串匹配**，分块边界变化就不再有影响。
> **→ 另需过滤【过短词】**：单字（如"我"）几乎任何屏幕都含它，零区分度。

**★★ 口径必须一致**：实测踩坑 —— 判定用 `_hit`（要求 len≥2）但采集漏了这一层，
单字"我"被收进签名却永远不可能命中 → **得分永远达不到 1.0**。
故过短词的过滤放在**提取阶段**，采集与判定走同一函数。

### 3. 布局【虚拟词】—— 把布局编码成词，复用同一套机制

`vision.ocr` 每块都带 `(x,y,w,h)`，原先只用了文字、完全没用位置。

**实测**：布局的**精确数值全都不稳**（块数 21/18/20 —— 和内容词一样随内容变）；
只有**离散/布尔特征**才可能稳（"底部导航 有·有·有" ✓，"键盘 无·无·有" ✗）。

> **→ 把布局编码成【虚拟词】（`§底部导航` / `§键盘` / `§内容密集` / `§顶栏`），
> 与真实文字混在一起走同一套多采样+高频过滤。不稳的自动被滤掉，稳的自己留下。零新算法。**

**★ 只做【单侧特征】**（条件成立才加词），不加"§无键盘"这类否定词 ——
后者在多个页面都成立 → 零区分度 → 只会稀释分数。

**★★ `§键盘` 用【按键文字计数】而非位置**：起初写"y>0.82 的块 ≥10"，
实测在搜索输入页只抓到 7 块（键盘顶部行在 y=0.719，被阈值挡在外面）→ 键盘弹着却判成"无键盘"。
而键盘按键文字是固定集合（ABC/DEF/…/空格/123），实测它们在签名里 3/3 稳定 → 直接用它们更鲁棒。

### 4. ★ `--expect` 前置校验 —— 防"把 A 页当成 B 页采下来"

**实测踩坑**：我把**抖音朋友页**当成**首页**采了签名 → 之后 `which` 判它 **1.00**，
**看起来完美，实则错标**。根因：两页都有"朋友/消息/我"，**光看 OCR 分不出来**。

> **`snapshot` 依赖"人来告诉它这是哪一页"；标错了签名就是错的，
> 而判定会【忠实地】按错签名工作。**
> **→ 故 `--expect`：采集前要求屏幕上出现指定文字，否则拒绝采集。**
> **实测它拦住了第二次同样的错误**（键盘遮住底部 tab，tap 没生效，我差点又采错）。

## 格式

```
pages/<app bundleId>/<页面名>.json
{
  "page": "搜索输入页(有键盘)",
  "app": "com.ss.iphone.ugc.Aweme",
  "env": { "screen": "750x1334", "lang": "zh-Hans", "collected": "...", "samples": 2, "match": "substring" },
  "hash": "<采集时的 pHash>",
  "signature": ["搜索", "语音搜索", "ABC", "§键盘", "§内容密集", "§顶栏", ...],  ← 只用高频词
  "freq":      { "搜索": 2, "§键盘": 2, ... },     ← 每个词出现几次
  "union":     ["…", "看看南京", …],               ← 诊断用，含内容词
  "rawCount": 36
}
```

## 用法

```bash
# 采集（★ 强烈建议带 --expect；键盘页用 --churn none）
python scripts/page.py snapshot "搜索输入页(有键盘)" --app com.ss.iphone.ugc.Aweme `
       --samples 2 --churn none --expect "搜索" --verbose

# 判定
python scripts/page.py which [--threshold 0.6]

# 验证（★ 采完必做）
python scripts/page.py verify "首页" --rounds 5

# 列表
python scripts/page.py list
```

**参数要点**：
- `--churn scroll|none`：采样之间怎么"换内容"。
  **`scroll`** 适合信息流（上滑换一条，结构不变）；
  **`none`** 适合静态页，**★ 也适合键盘页** —— 实测在搜索输入页上滑会**收起键盘**、
  结构被改变，签名会混入两种状态导致判定崩掉（0.14）。
- `--expect 文字`（可多次）：采集前置校验。**别省它。**
- `--samples N`（默认 3）· `--min-freq F`（默认 `samples-1`）。

## ★★ 采集纪律

- **采集时设备不能被人工接管**（`controlState` 非 `direct/gateway`）；护栏会挡住输入类操作。
- **★ 工具会自检"滚动有没有真的改变内容"**：若各次采样大串完全相同会告警并说明结果不可信
  —— 实测抖音首页滚动没生效过（滑过评论区被吸收），此时内容词会被误当稳定词。
- **★ 有键盘 / 无键盘是【两个不同的页面】**，应分别采集、分别命名。
  实测：`搜索输入页(有键盘) → tap(0.05,0.063) → 搜索输入页(无键盘) → tap(0.05,0.063) → 首页`
  —— 返回箭头点两次才是真的返回，第一次只是收键盘。
- **★ 同一页面换了 App 版本后应重采**（`env.collected` 记了采集时间）。
- **★★ 调 `vision.ocr` 必须显式传 `timeout`**：网关默认只给 5 秒，而它实测耗时 2~4.6 秒
  → 不传会随机吃 **HTTP 504**（`page.py` 内部已统一传 30s）。

## 现状

| 页面 | 状态 |
|---|---|
| 抖音 · 搜索输入页(有键盘) | **✓ 已采 · verify 5/5 · 平均 0.99** |
| 抖音 · 首页 | **⚠️ 已采但 verify 2/5（0.44）—— 动态页，OCR 方案不适用，待图标模板匹配（L0）** |
| 抖音 · 搜索结果页 / 朋友页 | ✗ 待采 |

**★ 已知局限（诚实记录）**：
1. **动态页（视频流）判定不稳** —— 结构特征是图标+小字，OCR 先天不可靠 → 需 L0 图标模板。
2. **`--churn none` 会让内容词混入**（实测"看看南京"等搜索建议进了签名）。
   当前可用是因为结构词占多数（22/30 → 最差 0.73 仍过阈值）；
   若要根治，需"换内容但不改结构"的方式（如打字换建议词）—— 暂按 YAGNI 不做。
3. 只有 2 个签名，**"多页之间互不误判"只测了 1 对**（首页 vs 搜索页 = 0.00 ✓）。
