## 2. 深度研究：iMessage Data Foundry（本地代码）

### 2.1 架构分层（生成与写入分离，我们应借鉴）

```
personas（虚拟人物档案）→ conversations（会话生成：内容+时间戳）→ db/schema（版本化 schema）→ builder（add_handle→create_chat→add_message→finalize）
```

- `conversations/`：generator（会话编排）、timestamps（时间戳拟真）、seeding（主题种子）
- `personas/`：models（Persona 数据模型）、storage（SQLite 持久化）
- `db/schema/`：base/sonoma/sequoia/tahoe 多版本 schema 镜像（纯 SQL 字符串，可 diff）
- `db/builder.py`：DatabaseBuilder 构建模式

### 2.2 时间戳拟真算法（核心可借鉴，`timestamps.py` + `constants.py`）

**① 昼夜权重表（CIRCADIAN_WEIGHTS）——「使用习惯」的核心**

| 时段 | 权重 | 语义 |
|---|---|---|
| 0-6 点 | 0.05 | 深夜（几乎无） |
| 6-8 点 | 0.30 | 早起 |
| 8-9 点 | 0.70 | 早高峰 |
| 9-12 点 | 0.90 | 上午工作 |
| 12-14 点 | 0.80 | 午休 |
| 14-18 点 | 0.95 | 下午 |
| 18-21 点 | **1.00** | **晚上峰值** |
| 21-23 点 | 0.70 | 晚间 |
| 23-24 点 | 0.30 | 睡前 |

实现：`_pick_weighted_time` 随机取时点，按权重接受（拒绝采样，最多 50 次）。

**② 会话簇结构（session-based）**
- 70% 消息进「会话簇」（5-30 条快速往返），30% 散落
- 会话内间隔 30s-5min（`min/max_session_gap_seconds`）
- 会话间：整个时间范围按会话数均分槽位（`slot_duration = total/num_sessions`），每会话落在槽内加权取起始点
- **抖动 jitter**：`base_delay × uniform(0.7, 1.3)`，避免机械规律

**③ persona 响应速度（per-person 拟真）**
- `RESPONSE_TIME_RANGES`：INSTANT 5-60s / MINUTES 60-600s / HOURS 1800-14400s / DAYS 43200-172800s
- 会话内每条消息的延迟按「当前回复方 persona」的响应速度取 + jitter(0.8-1.2)

**④ 输出 Apple 纪元纳秒**（`datetime_to_apple_ns`）——与我们实证的 `sms.db message.date=纳秒` 一致 ✓

### 2.3 Persona 模型（`personas/models.py` —— 虚拟人物档案）

```python
Persona:
  name / identifier(E.164或邮箱) / country_code
  personality（性格）/ writing_style（写作风格）/ relationship（关系）
  communication_frequency（HIGH/MEDIUM/LOW）
  typical_response_time（INSTANT/MINUTES/HOURS/DAYS）
  emoji_usage（NONE/LIGHT/MODERATE/HEAVY）
  vocabulary_level（SIMPLE/MODERATE/SOPHISTICATED）
  topics_of_interest（兴趣话题列表）
```

**启示**：每个虚拟联系人 = 一个 Persona（名字+号码+性格+响应速度+话题），通话/短信/通讯录三域共享同一组 Persona → 数据自洽。

### 2.4 DB 构建模式（`CLAUDE.md` 记录）

- **DatabaseBuilder**：`add_handle` → `create_chat` → `add_message` → `finalize`（先建 handle 再 chat 再 message，保证外键完整性）
- **一致性约束**：`handle.service` / `chat.service_name` / `message.service` 三表必须对齐（与我们踩坑一致）
- **GUID 唯一**：每条 message/attachment 唯一 guid
- **join 完整性**：无 `chat_message_join` 的消息不显示（印证）
- **批处理**：DB_WRITE_CHUNK_SIZE=500、重试 3 次
- **话题切换**：长会话（20+ 条）2%-5% 概率话题转换（`TopicShiftConfig`）

## 3. 落地映射到 SuperPhone 设备端（ObjC 自研）

| 模块 | 借鉴 | 设备端落地 |
|---|---|---|
| 虚拟联系人生成 | Persona 模型 | 自研 Persona 结构（姓名/号码/关系/响应速度/话题），三域共享同一组 |
| 姓名/号码池 | Faker zh_CN 池思想 | 自研中文姓/名池 + 真实号段池（13x/15x/17x/18x/19x），去重 |
| 通话时间分布 | 昼夜权重 + 会话簇 | 通话按昼夜权重分布，未接/已接/呼入呼出类型分布（参照 FakeDetail 枚举） |
| 短信会话拟真 | **session 会话簇 + 昼夜权重 + persona 响应速度 + jitter** | 70% 会话簇/30% 散落，间隔按响应速度，昼夜加权，jitter 抖动 |
| 时间戳 | Apple 纪元纳秒（短信）/秒（通话） | 已实证定稿（说明文档 4.8） |
| 写入 | DatabaseBuilder 分层 | 生成器=纯函数输出结构化数据 → 写入层按 4.8 定稿格式落库 |
| 可复现 | seed | 随机种子参数 |

## 4. 结论

最值得借鉴的是 **iMessage Data Foundry 的时间戳拟真算法（昼夜权重 + 会话簇 + persona 响应速度 + jitter）和 Persona 体系**——这是"数据看起来像真人用的"核心。设备端无 LLM，会话内容用「内容池模板」替代 AI 生成；时间戳算法可直接移植为 ObjC（纯逻辑，无依赖）。通话记录直写方式已被 kfatehi 的 Ruby 脚本独立印证（与我们实证的 ZCALLRECORD 字段一致）。

## 5. Persona Schema 定稿（2026-08-24）

按「常住地 Profile + 关系分层 + 备注模式 + 频率传导」模型定稿。**通讯录是"一个人"的通讯录**，一切从常住地 Profile 推导。

### 5.1 生成输入：常住地 Profile

```
TRProfile:
  city          常住城市（决定本地 HLR 池，如 北京）
  province      省份
  carrier       本人运营商（移动/联通/电信，决定号段份额）
  selfPhone     本人号码（生成 +86 与账户关联）
  contactCount  目标联系人数量（默认 30-50）
  seed          随机种子（可复现）
```

### 5.2 输出：Persona（联系人档案，ObjC 结构）

```
TRPersona:
  name             显示名（备注模式决定：张伟 / 爸爸 / 张师傅 / 快递小李 / XX银行客服）
  familyName       姓（CNContactStore 写入：全名放单字段）
  givenName        名（可空）
  phone            裸号 11 位（如 13801234567）
  phoneE164        +86 前缀（handle id 存储用）
  city / province  归属地（决定号段与 HLR 前缀）
  layer            分层枚举：local / family / nation / service / business
  remarkStyle      备注模式：realName / kinship / occupation / service / company / nickname
  rank             联系频率 1-5（→ 通话/短信生成量权重）
  creationDaysAgo  创建距今天数（→ CreationDate，关系决定：家人/老同学早，快递/家政近）
  email            可选（同事/客户）
  address          可选（快递）
  birthday         可选（生日 MM-DD，家人/密友）
  hasAvatar        可选（家人/密友有头像）
  phone2           可选第二号码（家庭/工作，同一 Persona 多号）
  nickname         可选（昵称，如 阿强 / 老李）
```

### 5.3 分层配置（默认占比，可调）

```
local  55-65%  同城熟人（同事/同学/朋友）——真实姓名，本地 HLR，最高频
family 10-15%  家人亲戚——关系称谓备注（爸爸/二姨/三舅），本地+老家异地
nation 10-15%  全国社交（老同学/客户/网友）——异地 HLR，CreationDate 早
service 8-10%  生活服务（快递/家政/维修/电工/物业）——职业+姓备注，同城，最近才存
business 2-5%  机构商家（银行/运营商/4S店）——公司名备注，400/95xxx 机构号
```

### 5.4 生成流程

1. Profile 定常住城市/运营商 → 推导本地 HLR 号段池 + 号段份额
2. 按分层占比分配各层数量
3. 每层生成 Persona：号码（本地 HLR / 异地城市 HLR / 机构号段）、备注模式、rank、创建时间、可选元数据
4. 全局号码去重（含设备已有联系人） + seed 可复现

### 5.5 频率传导（→ 通话/短信生成器的输入）

- `rank` 1-5 决定该联系人的通话条数/短信条数权重（家人密友 rank 高）
- `layer=service`：几乎只有短信（取件码/预约确认），极少通话
- `layer=business`：偶尔联系（10086/银行通知）
- 通话/短信的号码**从通讯录 Persona 池引用**（三域自洽）

### 5.6 写入映射（CNContactStore）

```
TRPersona → CNMutableContact:
  familyName   = name（全名放单字段，避免"姓 名"反序）
  phoneNumbers = @[phone, phone2]（CNLabelPhoneNumberMobile / Home）
  emailAddresses = email（可选）
  postalAddresses = address（可选）
  birthday     = birthday（可选）
  imageData    = 头像（可选）
```

**频率传导的 rank 同时用于通话/短信层——通讯录生成器输出即为三域共用的 Persona 池。**
