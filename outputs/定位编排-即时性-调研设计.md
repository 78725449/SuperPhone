# 定位编排 · 联动性设计

> 目标：**前端（App 地图页）定义 = 设备端实际执行**，编辑即生效、即时可感知。
> 核心洞察：**所有编排变动（增/删/重排/模式）始终基于当前位置**——两端无需互相理解锚点/段结构，
> 联动契约只有一句话：**"App 写完整新轨迹，daemon 从当前位置续播"**。

---

## 1. 联动闭环（唯一关注点）

```
                    ┌──────────────── 联动闭环 ───────────────┐
                    │                                          │
  App（唯一真相）    │       写完整新轨迹文件 + notify           │
  当前位置 + 编排段 ─┼────────────────────────────────────────▶ daemon（哑执行器）
  （编辑：增/删/     │        （完整 points，非增量）             │ 收到即重载，
    重排/模式）     │                                          │ 从当前位置最近点续播
                    │◀─────────────────────────────────────────┘ 注入 locationd
                    │   写回 mobile plist（当前位置+速度）
                    │              │
                    │              ▼
                    │   地图位置：locationd→原生 MKUserLocation（事件驱动，即时）
                    │   状态栏/锚点红蓝/出行图标：事件推送即时刷新
                    └──────────────────────────────────────────┘
```

**不变锚点 = 当前位置**：
- App 编辑重算的截断基准 = daemon 写回位置（`currentSimPosition` 读 mobile plist）。
- daemon 续播起点 = 它自己当前注入位置（`_startTrack` 最近点续播）。
- 两端都不猜对方："App 不猜 daemon 在哪"、"daemon 不猜从哪播"。

---

## 2. 联动契约

| 项 | 契约 | 现状 |
|---|---|---|
| 手递手数据 | App 写**完整新轨迹**文件（原子写） | ✅ `writeTrackFile` |
| 触发 | `notify("prefs-changed")` → manager 订阅 → `reloadFromPrefs` | ✅ 近实时 |
| 变更感知 | daemon 参数指纹含**轨迹文件 mtime** | ✅ 已修（新轨迹必重载） |
| 播放起点 | daemon **从当前位置最近点续播**（不从头重放） | ✅ 已修 |
| 停止语义 | 删除全部 → 写 `mode=off` | ✅ 已修 |
| 地图位置反馈 | 原生 `MKUserLocation`（模拟=模拟位置/关闭=真实位置） | ✅ 已修 |
| 跟随 | 原生 `MKUserTrackingModeFollow`（拖动自动退出） | ✅ 已修 |

**结论：联动闭环主干已通。** 剩余两处补丁（见 §3）补全"编辑不丢"与"反馈即时"。

## 3. 剩余补丁（最小实现）

### 3.1 编辑不丢（生成中挂起合并）

**问题**：算路（MKDirections，百ms~秒）期间 `isGenerating=YES`，`commitItinerary`/`regenerateFromIndex` 直接 return——
锚点已入 `segments` 但轨迹未扩展，编辑被静默丢弃，打破联动连续性。

**实现**（App 侧）：
```objc
@property (nonatomic, copy) void (^pendingEditAction)(void); // 生成中挂起的最新编辑

- (void)runEdit:(void (^)(void))action {
    if (self.isGenerating) { self.pendingEditAction = action; return; } // 合并：最后一次生效
    action();
}
```
- 编辑入口（`handleTap`/`applySearchResult`/`confirmRegionConfig` 的 `commitItinerary`、
  `deleteSegmentAt`/`moveSegmentFrom` 的 `regenerateFromIndex`）改走 `runEdit`。
- `commitItinerary` 与 `regenerateFromIndex` 的 completion 里 `isGenerating=NO` 后：
  `if (pending) { pending = nil; pending(); }`（安全重入，追加/删除语义由各自入口保证）。

### 3.2 反馈即时（事件推送）

**问题**：状态栏坐标/速度、锚点经过红/蓝、当前位置出行图标靠 **1s 轮询 plist**，有 ≤1s 感知延迟。

**实现**：
- daemon：注入点（`_injectPointDict`/`_anchorTick`）注入后 `notify_post("com.82flex.trollvnc.locsim-update")`（mobile plist 位置写回已删除，locationd 为唯一位置真相）。
- App：`notify_register_dispatch(…, dispatch_get_main_queue(), handler)`（已有先例），
  handler 内复用 `refreshLiveStatus` 的刷新逻辑（读 locationd → 状态栏/锚点状态/出行图标）。
- 1s 轮询定时器保留作兜底（事件与轮询同幂，不冲突）。

## 4. 明确不做（避免过度设计）

- ❌ 不在 App↔daemon 间引入 socket/命令协议——同设备 IPC（文件+notify）已足够。
- ❌ 不走能力注册表（那是外部契约）；App 内部只走同设备通道。
- ❌ 不做算路段缓存/段级同步——"完整新轨迹 + 当前位置续播"已覆盖所有编辑语义。
- ❌ daemon 巡检保留为失效恢复兜底，不承担"发现变更"职责。

---

## 5. 验证

1. 编辑锚点（增/删/重排）→ 设备定位**即时续播**（状态栏坐标逐秒变化，无跳回起点、无冻结）。
2. 快速连点 3 个锚点 → 三条路线全部生长，无丢段。
3. 删除全部 → 设备恢复真实定位。
4. 注入时状态栏/锚点红蓝/出行图标**即时**刷新（无 1s 迟钝）。
5. 回归：设备端 CI 编译（bootstrap .tipa）；网关套件不受影响（无网关改动）。
