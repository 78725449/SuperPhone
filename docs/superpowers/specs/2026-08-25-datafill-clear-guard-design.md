# 数据填充：清空残留校验 + 短信通讯录依赖校验（设计规格）

> 日期：2026-08-25
> 状态：已批准（用户定案）
> 前置依据：《2026-08-24-calls-sms-generator-design.md》（依赖校验 §3.3 L191）、《说明文档.md §4.8》、AGENTS.md「数据填充行为定稿」

## 1. 背景与问题

### 1.1 用户观察到的现象

1. **"已删除的通讯录号码一直出现"**：用户曾反馈生成通话记录时反复出现已删除的通讯录号码。
   - **排查结论**：通话生成号码只来自两个源——实时枚举 CNContactStore 的当前通讯录（contact 选人 70%）与随机陌生号（trRandomPhone，不可能精确复现旧号码）；通话生成从不读历史 CallHistory。
   - **真机验证**（2026-08-25）：清空通讯录后系统通讯录 App 为空，此时点击生成通话 → 正确提示"通讯录为空，请先生成通讯录"；短信仍可正常生成。
   - **最终判断**：当前版本清空有效（此前"旧号码反复出现"最可能来自旧版本 `deleteContact` 传 immutable 快照静默失败 bug，或当时 iCloud 同步回写残留）。为防未来再次出现"看似清空、实际未删干净"且无感知，需加**清空后校验 + 残留报错**兜底。

2. **"没有通讯录时短信能正常生成，正常吗？"**
   - **排查结论**：短信构成 90% 为服务类（验证码/快递/银行/运营商/营销），设计上"不落通讯录"，脱离通讯录可生成属**设计内行为**（设计文档 §2.2）。
   - **两端分叉（真问题）**：family 类（10%）在通讯录为空时——Node 端 `phone:null`（无号码纯会话）；ObjC 端退化 `trRandomPhone()` 随机号，该号码在通讯录反查不到，**违背"反差确认"语义**。
   - **用户决策**：短信也加依赖校验，通讯录为空时整体报错拦截（严格遵循设计文档 §3.3 L191），消除"查不到的家人号码"。

## 2. 方案

### 2.1 改动 1：清空联系人后校验 + 残留报错（`TRDataFiller.mm` `clearDatabase` contacts 分支）

- 现有删除循环之后，重新 `enumerateContactsWithFetchRequest`（keys 仅 `CNContactIdentifierKey`，轻量）统计 `remaining`。
- `remaining > 0` → 返回 `ok:NO` + `cleared`（已删条数）+ `remaining`（残留条数）+ `error`："仍有 N 条联系人未能删除（可能来自 iCloud 同步/只读账户/SIM 卡），请检查 设置→通讯录→账户"。
- `remaining == 0` → 维持 `ok:YES`（现有结构不变）。
- 校验枚举本身失败 → `errors` 追加"清空后校验失败"，维持 `ok:YES`（删除已执行，仅提示）。

### 2.2 改动 2：短信生成加通讯录依赖校验（`TRDataFiller.mm` `trFillSms`）

- 生成前读通讯录（现有 famPool 读取位置提前为强制校验），通讯录为空 → 返回 `{ok:NO, error:"通讯录为空，请先生成通讯录（家人朋友短信依赖通讯录）"}`。
- 与通话生成校验（`trFillCalls`）语义一致（设计文档 §3.3 L191）；通讯录非空时 family 类照旧使用家人号码。
- **Node 端不动**：`generateSms` 作为纯算法原型保持"可脱离通讯录生成"能力（family `phone:null`）；设备端依赖校验属**产品层约束**——算法层提供能力、产品层加门禁，在文档中标注分层。现有 6 条短信测试断言（npm test）不受影响。

### 2.3 改动 3：文档同步（项目纪律）

- AGENTS.md「数据填充行为定稿」补两条：清空残留校验行为、短信通讯录依赖校验。
- 说明文档.md §4.8 对应条目同步。
- CodeWiki.md 相关行号/数量/描述校准。

## 3. 接口契约变化

- `clearDatabase("contacts")` 返回结构向后兼容：`ok:YES` 保持；残留场景新增字段 `remaining`（NSNumber），此时 `ok:NO` + `error`（含残留数）。
- `data.sms.fill` / `data.sms.generate` 通讯录为空时返回 `{ok:NO, error:"通讯录为空，请先生成通讯录（家人朋友短信依赖通讯录）"}`。
- UI 无需改动：`clearAll:` / `generate:` 已有 `ok:NO → 显示 error` 逻辑。

## 4. 边界

- calls/sms 清空分支不动（sqlite 直写 DELETE，无静默失败问题）。
- 通话生成依赖校验已存在，不动。
- Node 端零改动，`npm test` 不受影响。

## 5. 验证门槛

1. 设备端改动 → CI bootstrap 编译通过（App target 改动仅在 bootstrap job 暴露错误）。
2. 真机三条路径：
   - 清空通讯录 → 短信生成报"通讯录为空，请先生成通讯录"；
   - 生成通讯录后 → 短信正常生成（family 用家人号码）；
   - 清空残留场景（SIM/只读账户联系人存在时）→ 报错含残留数，UI 显示"清空失败：仍有 N 条…"。
