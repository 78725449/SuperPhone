# 通话记录 & 短信生成器 · 实现规格（Design）

> 日期：2026-08-24
> 前置依据：《2026-08-24-contacts-generator-design.md》（通讯录规格，备注模式互斥可反查约束）、《说明文档.md §4.8》（sms.db/CallHistory 写入格式定稿）、《2026-08-24-数据生成算法-开源调研.md》（时间戳拟真/会话簇算法）
> 输入：**读系统通讯录** + 生成算法"逆"反查角色（无演员表、无持久化）

## 1. 目标与范围

在 SuperPhone 上实现**通话记录生成器**与**短信生成器**：用户配置（数量/时间范围/运营商）点击生成 → 设备端读系统通讯录并按备注名反查角色选人，按拟真算法生成通话/短信写入系统库（CallHistory.storedata / sms.db），系统电话/信息 App 可见。

**范围**：
- ✅ 通话记录生成（通讯录+陌生号池重复度 + 时段微调 + 状态拟真 → ZCALLRECORD）
- ✅ 短信生成（服务短信为主 + 内容池 + 时间分布 → sms.db）
- ✅ 角色反查（读系统通讯录 + 生成算法"逆"映射角色，无演员表持久化）
- ✅ 配置表单（数量 + 时间范围 + 运营商）+ 伪装页「通话/短信」标签
- ✅ 设备端能力 + 网关中转 + 前端全链路
- ❌ 改定位（另一窗口）；伪装页载体同通讯录规格

## 2. 生成模型

### 2.1 依赖与输入：读系统通讯录 + 生成算法反向映射（2026-08-24 定稿，无演员表）

通话/短信生成时**直接读系统通讯录（CNContactStore）** 作为 Persona 池，用**通讯录生成算法同一份词池（TRRoleLexicon）** 的"逆"精确判定每个联系人的角色——**三能力（通讯录生成/通话/短信）共用同一套词池算法**（通讯录规格 §2.4）：

| 角色 | 匹配来源（TRRoleLexicon 词池） | 备注名示例 |
|---|---|---|
| family | 称谓词池 | 爸爸、二姨、三舅 |
| service | 职业词池 | 张师傅、快递小李 |
| business | 机构词池 | XX银行、10086 |
| work | 公司词池（含 `-` 或职位词） | 李强-腾讯、王丽-XX科技 |
| friend | 兜底：以上都不匹配 | 张伟、李娜 |

匹配顺序：family → service → business → work → friend（互斥保证不重叠，单一数据源零漂移，生成能识别的必能反查）。

- **自己生成的通讯录 100% 可识别**（备注名按互斥规则生成）；系统原有联系人同规则尽力识别
- 频率 rank：无精确来源 → 按分层加权近似（family/work 高、service/business 低）
- **无需演员表持久化、无依赖顺序、无状态**——三域天然一致（读的就是通讯录本人）

### 2.2 通话记录生成逻辑

**输入参数**：`{ count, days, carrier }`（count=条数、days=最近 N 天、carrier=本人运营商）

**选人（两池 + 陌生号重复度涌现"记住的号"，2026-08-24 定稿）**：
1. **通讯录内**（主，~70%）：读系统通讯录，按反查角色分层加权选（family/work 高权重、service/business 低）
2. **陌生号池**（~30%）：生成不在通讯录的号码，按 **Zipf 重复度分布**（少数号高频、多数号低频）：
   - **高频复用号**（占通话量 ~15%，单号重复 3-10 次）→ **即"记住的号"**：Recents 显示裸号但用户认识（10086 客服、常叫外卖、家人裸号由固定高频体现）——**不需要预先标记谁是熟人，重复出现即"认识"**
   - **低频一次性号**（占 ~15%，单号 1 次）→ **真陌生**：推销/骚扰/临时，未接来电集中在此

**分层加权与占比（反查后近似 rank，2026-08-24 定稿；占比可配置）**：
```
family 4.0 / work 3.0 / friend 2.0 / service 1.0 / business 0.5（选人权重，越大越常联系，固定）
状态占比 ratios{incoming,outgoing,missed}（可配置，默认 呼入 40% / 呼出 40% / 未接 20%，合计 100%）
选人池占比 ratios{contact,stranger}（可配置，默认 通讯录 70% / 陌生号 30%，合计 100%）
```

**时间（rank 主 + 时段微调）**：
- 时间戳在最近 N 天回落，按昼夜权重分布（0-6 点权重 0.05、18-21 点峰值 1.00）
- 白天（9-18）同事/客户/机构层权重略高；晚上（18-23）家人/密友略高；深夜整体极低频——**任何池任何时段都可出现，只调概率**
- **活跃日/沉寂日**：随机选 1-2 天为活跃日（通话密集），其余稀疏

**状态拟真**：
- 未接集中在陌生号/推销（忙碌时段），家人朋友偶尔漏接
- 时长：对数分布（`-ln(U)×120` 秒，U∈(0,1)，即 30s-2min 短通话为主；family 长通话 30% 概率 10-30min），未接=0
- 连续通话：同一人多条紧挨（间隔几秒-几分钟，占 ~15%）
- 通话号码若在通讯录 → Recents 显示名；否则显示裸号

**写入**：`CallHistory.storedata` → `ZCALLRECORD`（格式见说明文档 §4.8：ZDATE 秒、Z_PK max+1 同步 Z_PRIMARYKEY、补 ZVERIFICATIONSTATUS=4 等辅助字段）

### 2.3 短信生成逻辑

**输入参数**：`{ count, days, carrier }`

**构成比例（2026-08-24 定稿——服务短信为主，日常对话点缀；比例可配置 ratios{code,express,bank,carrierSms,marketing,family}，合计 100%）**：
现实中国设备短信几乎全是服务类（家人朋友走微信/社交软件，极少发短信；POC 实证真实短信全为验证码/快递/运营商类）：
```
验证码类    35%（抖音/微信/银行/电商/外卖）
快递类      20%（取件码/签收通知）
银行/金融   15%（账单/转账通知）
运营商      10%（carrier 服务短信：账单/余额/流量）
营销/推广   10%（房产/贷款/课程/电商促销——陌生号）
家人/朋友   10%（少量简短 1-3 条，如"好的""到家了吗"）
```

**选人建会话**：
- 服务/陌生类（占 90%）：生成服务号/陌生号（不落通讯录），单条发送（验证码/快递/银行/营销）
- 家人/朋友（占 10%）：从反查 family/friend 层选，简短 1-3 条（不用社交软件的人少数几条），不做 5-20 条长往返
- carrier 服务短信：1-2 条（运营商账单/余额提醒）
- **未接来电联动**：若最近通话有未接陌生号，跟 1 条"您有一个未接来电"短信

**内容池模板（2026-08-24 定稿，静态常量，随机选 + 随机数字注入）**：

| 类 | 模板（{x}=随机注入） |
|---|---|
| 验证码 | `[抖音] {4位码} 是您的验证码，5 分钟内有效。`、`【微信】验证码 {4位码}，请勿泄露给他人。`、`[XX银行] 您的登录验证码 {6位码}`、`【京东】您的验证码 {6位码}，用于登录/支付`、`[饿了么] 本次登录验证码 {4位码}` |
| 快递 | `您的包裹已到{驿站名}驿站，取件码 {4位码}`、`【{快递公司}】您的快件{单号}已签收，感谢使用`、`您的快递已放在{柜号}号柜，取件码 {4位码}` |
| 银行/金融 | `您尾号{4位}的账户{时间}消费 {金额} 元`、`您尾号{4位}的账户收到转账 {金额} 元`、`您尾号{4位}的信用卡本期账单 {金额} 元，还款日 {日期}` |
| 运营商 | `您本月已使用流量 {x.x} GB，剩余 {x.x} GB`、`您的话费余额 {x} 元，请及时充值`、`【{运营商}】您的套餐即将到期，可登录 APP 续订` |
| 营销/推广 | `【{楼盘}】{楼盘名} 现房热销，首付{万}万起，来电咨询{电话}`、`【{机构}】您可申请{金额}万额度贷款，点击链接查看`、`【{平台}】{商品} 限时 5 折，立即抢购` |
| 日常对话（friend/family，少量） | `到家了，你那边怎么样？`、`好的，知道了`、`周末有空吗？` |

- 服务/陌生类（验证码/快递/银行/运营商/营销）占 90%，单条发送，发送方为陌生号/服务号
- 家人/朋友日常对话仅 10%，简短 1-3 条（不做长往返，符合"社交软件替代短信"现实）
- **未接来电联动**：运营商"您有一个未接来电"短信（`【运营商】您有一个来自{号码}的未接来电`）

**时间（服务短信单条散落为主，对话小簇为辅）**：
- 服务/陌生类（90%）：**单条散落**，按昼夜权重分布——验证码/快递/银行多在白天工作时间（9-18）、电商推送/营销多在晚间（19-22）
- 家人/朋友日常（10%）：偶尔 2-5 条小簇（簇内间隔 30s-5min），jitter ×0.7-1.3
- 输出 Apple 纪元**纳秒**（×1e9）

**写入**：`sms.db` → `message` + `chat` + `handle` + `chat_message_join` + `chat_handle_join`（格式见说明文档 §4.8：date 纳秒、service=SMS、chat style=45/state=3/account_login/last_addressed_handle、handle UNIQUE 复用）

### 2.4 运营商（carrier）用途

通话/短信表单提供**本人运营商选择**（移动/联通/电信，默认移动）：
- 通话：运营商客服短号（10086/10010/10000）呼入/呼出 1-2 条
- 短信：运营商服务短信（账单/余额/流量提醒）1-2 条

## 3. 配置表单设计（伪装页「通话/短信」标签，原生 UI）

## 4. 接口契约

### 4.1 设备端能力（TRCapabilityRegistry）

```
cap: data.calls.generate
params: { count, days, carrier, ratios{contact,stranger,incoming,outgoing,missed}, seed }
返回: { ok, created: N }        // 写入 ZCALLRECORD 条数

cap: data.sms.generate
params: { count, days, carrier, ratios{code,express,bank,carrierSms,marketing,family}, seed }
返回: { ok, created: N }        // 写入 message 条数
```

实现：新文件 `src/TRCallsGenerator.mm` / `src/TRSmsGenerator.mm`（生成逻辑纯函数）+ 读系统通讯录（CNContactStore）按备注名反查角色 + 写入层复用 data.test 已验证的 ZCALLRECORD / sms.db 逻辑。

### 4.2 网关中转（server/index.js，外部走能力通道）

```
POST /api/devices/:id/calls-generate → sendDeviceCmd invoke data.calls.generate
POST /api/devices/:id/sms-generate   → sendDeviceCmd invoke data.sms.generate
```

复用 /contacts-generate 模式（校验参数 + 隧道 invoke + 504 超时）。

### 4.3 双入口（2026-08-24 架构定稿——统一落到 TRCapabilityRegistry）

同通讯录规格 §4.3：生成器在 daemon 单份实现，两入口最终都落在 TRCapabilityRegistry（与改定位 sim.location.* 同一机制）：

| 入口 | 调用方 | 路径 |
|---|---|---|
| **5802 HTTP 通用 invoke** | App 伪装页（原生，同设备） | `127.0.0.1:5802` POST `{"op":"invoke","cap":"data.calls.generate"/"data.sms.generate","params":{...}}`（5802 通用 invoke 转发 TRCapabilityRegistry） |
| **隧道 CMD invoke** | 外部（网关/5801） | sendDeviceCmd → TRCapabilityRegistry |

## 5. 伪装页集成（App 内，原生页面）

> 🖥️ **交互原型（UI 定稿参照）**：`outputs/locsim-app-prototype.html`——浏览器打开即可验证四 Tab（位置模拟/联系人/通话/短信）全部交互与最终 UI 形态；后续 UI 开发以该原型为准。

伪装页 = **App 第三 Tab（控制后、设置前）原生页面**，四标签：改定位（daemon 能力已实现）/ **生成通讯录** / **生成短信** / **生成通话记录**。载体与 UI 定稿同通讯录规格 §5.2/§5.4（原生表单直调 `127.0.0.1:5802`，三段式布局 + 占比滑块 + 合计校验）。生成后 kill 对应 daemon（callservicesd/imagent）生效，无 respring。
> ⚠️ **respring 已禁用（2026-08-24 项目红线）**：respring（kill SpringBoard）会重启主屏，中断前台 App、打断隧道/注册会话、破坏 daemon 保活链路；数据直写系统库后 kill 对应 daemon（callservicesd/imagent/contactsd）即可让系统 App 读取新数据，respring 属冗余设计。**全文所有涉及 respring 的描述一律作废**，刷新只允许 kill 对应 daemon，禁止按 respring 实现/回归。

## 6. 实现分层

```
┌ App 伪装页（第三 Tab 原生页面：通讯录/通话/短信标签）
├ 设备端 5802 通用 invoke（App 直调入口，转发 TRCapabilityRegistry）
├ 设备端能力（TRCapabilityRegistry，外部入口）
├ 设备端写入层（CNContactStore / ZCALLRECORD / sms.db，已验证）
├ 设备端生成器（TRContactsGenerator / TRCallsGenerator / TRSmsGenerator，纯函数）
└ 角色反查模块（TRContactRoleResolver：读系统通讯录 + TRRoleLexicon 匹配 → 角色）
```

**实现顺序**：通讯录生成器 → 角色反查模块 → 通话生成器 → 短信生成器。

## 7. 验证方案

1. **生成器单测**：固定 seed → 通话条数/状态分布/时长分布合理、号码来自通讯录+陌生池、**陌生号重复度符合 Zipf（少数高频=记住的号/多数低频=真陌生）**；短信构成比例（服务 90%/日常 10%）与时间分布符合配置、内容池模板随机注入；角色反查对互斥备注名 100% 命中
2. **端到端**：先生成通讯录 50 → 生成通话 20/短信 30 → 系统电话/信息 App 可见 → 通话显示联系人名 → kill daemon 后仍存在
3. **依赖**：通讯录为空时调用返回"通讯录为空，请先生成通讯录"
4. **回归**：网关 npm test 全过；设备端 CI 编译通过
