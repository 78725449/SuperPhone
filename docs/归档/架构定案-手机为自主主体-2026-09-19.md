## 一、★ 这不是"推翻架构"，是【拆层】

**原来黏在一起的两件事被拆开了**：

```
【旧形态】
  电脑上的 agent = 【agent 循环】+【模型】   ← 两件事绑死在同一台机器
  手机           = 哑执行器                 ← 只能被逐步指挥
  ✗ 手机离不开电脑（电脑关机即废）
  ✗ 22 台设备都想用模型 → 都挤同一台电脑
  ✗ "谁算客户端"模糊

【新形态】
  手机 = 【agent 循环】+【技能库】          ← ★ 自主主体
  AI   = 【可插拔服务】                     ← ★ 本地 / 局域网 / 云端，随便换
  电脑 = 【两个可选角色之一】                ← ★ 命令入口 + AI 服务提供方
  ✓ 手机有自主性（命中技能卡时零 AI，完全独立）
  ✓ AI 可替换（手机不关心是哪个）
  ✓ 客户端定义清晰（下达命令的那个）
```

**★★ 主干哲学【一条没变】** ✓：
```
· 角色分层：导演 / 演员 / 引擎
· 公理一「少走视觉」—— 先查表，表不行才视觉
· 零模型回放 —— 技能卡回放不花模型
· 资产结构：任务表 / 页面表 / 技能卡 / 做法表
· 三视角体感：学（首次）/ 用（第二次）/ 复制（蜂群）
```

## 二、★★★★ 四层架构（四个独立可替换的层）

```
┌───────────────────────────────────────────────────────────────┐
│ ① 命令下达者（MCP 客户端）                                      │
│    控制台说人话 / 脚本 / iOS 快捷指令 / 另一个 agent / 定时任务   │
│    ★ 唯一"真正的客户端"                                        │
└───────────────────────────────┬───────────────────────────────┘
                                │ 一条命令（结构化，不是自由文本）
                                ↓
┌───────────────────────────────────────────────────────────────┐
│ ② ★★ 手机 = 自主主体（MCP 服务端）                             │
│    · 收命令                                                    │
│    · 查技能库 → 命中即回放（★ 零 AI，秒级）                    │
│    · 未命中 → 向 ③ 请求【规划】→ 执行 → 沉淀技能卡              │
│    · 执行中卡住 → 向 ③ 请求【判断/恢复】→ 更新做法表            │
│    · 自带验证（screen.hash / vision.ocr / expect 断言）         │
│    · 执行器：script.exec（★ 一次往返跑完整套）                  │
└──────────┬────────────────────────────────────┬───────────────┘
           │ 仅在三种时刻请求（可配地址）        │ 始终
           ↓                                    ↓
┌──────────────────────────────┐  ┌──────────────────────────────┐
│ ③ AI 服务（★ 可插拔）          │  │ ④ 设备原语（64 个能力）       │
│    · 手机上本地小模型          │  │    touch.tap / app.open       │
│    · 局域网内你的电脑（DSH /   │  │    vision.ocr / find_text     │
│      llama-server）            │  │    screen.hash / waitStable   │
│    · 云端 API                  │  │    script.exec                │
│    ★ 手机不关心是哪个          │  │    ★ 真正的"手"               │
└──────────────────────────────┘  └──────────────────────────────┘
```

**★★ 三条关键规则**：
1. **命令是【结构化】的**（`open_app{name:"抖音"}`），不是自由自然语言
   —— "人话→命令"的翻译归 ① 客户端（有 LLM 的做，没 LLM 的人自己打字）
2. **执行过程【不请求 AI】** —— `script.exec` 一次跑完，零模型
3. **AI 只在三处被请求**：规划 / 判断 / 恢复（见 §四）

## 三、★★★★ 三视角体感走查（AGENTS.md 第 6 条强制要求）

> **纪律**：架构级调整必须先从**实际使用角度**讲清三种情形下的**直观流程**，
> 并说明该调整**对操作造成的影响**。以下为本次调整的体感走查。

### ① 首次执行任务（探索期／"学"）—— 最贵的一次

**你会看到**：
```
你（控制台）：「打开抖音，搜索南京美食，看 3 个作品」
     ↓
手机：技能库查不到 → 向 AI 服务请求【规划】
     ↓ AI 回一份 steps 草图（不是每个动作都问，是一次给一份计划）
手机：script.exec 跑这份 steps
     ↓ 每步自带验证（wait_for / expect）
某步失败 → 向 AI 请求【恢复】→ 修正 steps → 重试
     ↓
成功 → ★ 沉淀成技能卡（意图 + steps + 环境指纹）+ 上报中心
     ↓
你看到：结果 + 「已学会，下次 3 秒内完成」
```

**影响与代价**：
- **时间**：**仍然慢**（几十秒到几分钟），因为要 AI 规划 + 可能重试
- **但产出**：**技能卡 + 做法表（含踩过的坑）** —— 这是**唯一一次值得付的学费**
- **★ 与旧形态的差别**：**规划与执行都发生在手机侧**，电脑只是被"请求"了一次

### ② 第二次执行任务（回放期／"用"）—— 零模型、秒级

**你会看到**：
```
你（控制台）：「打开抖音，搜索南京美食，看 3 个作品」
     ↓
手机：技能库★命中 → 直接 script.exec 回放
     ↓ 全程零 AI 调用、一次网络往返
成功 → ★ 验证计数 +1，上报中心
     ↓
你看到：★ 2–5 秒后出结果
```

**影响与代价**：
- **时间**：**100–160 秒 → 2–5 秒**（快 30–50 倍，见 §五的时间账）
- **风险**：**界面变了可能失效** → 走降级链 → 实在不行回落到①重新学
- **★ 与旧形态的差别**：**旧形态这条路径根本不存在**（每步都要模型看图）

### ③ 蜂群执行（N 台复制／"复制"）—— 一次学会全群拥有

**你会看到**：
```
1 台手机学会「打开抖音搜南京美食」
     ↓ 上报中心（技能卡 + 环境指纹 + 验证计数）
中心：合并 / 去重 / 冲突检测 / 灰度判定
     ↓ 达标后下发
其余 21 台：拉取到这张卡 → ★ 直接可用，无需各自再学一遍
     ↓
22 台同时跑同一个意图 → 每台各自验证计数 +1
```

**影响与代价**：
- **收益**：**一次学会全群拥有**（省 21 次学费）
- **★ 风险（必须靠护栏压住，见 §六）**：
  - **失败放大** —— 一条坏经验同步到 22 台 = 22 台一起坏
  - **行为同质化** —— 全群走同一条路径，平台反爬/限流时一起被识别
  - **技能库并发写** —— 22 台同时上报，中心要处理并发
- **★ 与旧形态的差别**：**旧形态没有"经验"这个东西**（每次都是现场推理）

## 四、★★★ AI 被请求的三个时刻（不是"每步看着办"）

| 时刻 | 触发条件 | 请求什么 | 频率 |
|---|---|---|---|
| **① 规划 Plan** | 技能库**未命中** | 「这个意图该分几步、每步做什么」 | **每个新意图一次** |
| **② 判断 Judge** | 需要【理解屏幕语义】时 | 「屏幕上这段文字是什么意思 / 这是不是我要找的页面」 | **低频**（多数判断由 `expect`/`vision.find_text` 零模型完成）|
| **③ 恢复 Recover** | `script.exec` 某步失败 | 「这步失败了，替代方案是什么」 | **异常时才发生** |

**★★ 关键**：**执行过程本身【不请求 AI】** ✓
**→ 这是"快"的根本原因，也是"零模型回放"的落地**

**★★★ 对模型能力的要求因此【大幅降低】** ✓✓✓：
```
GUI agent 模式：每步模型看图出坐标 → 必须极强 + 极快 ✗
本架构：      模型只在规划/判断/恢复时被请求
              输入是【结构化信息】（技能库、OCR 文字、页面签名），不是像素
              → ★ 本地小模型够用（现用的 GUI-Owl-1.5-4B 量级即可）
```

## 五、★★★★ 时间账（"极速"从哪来）

| 阶段 | 旧形态（模型逐步编排）| 本架构（技能卡回放）|
|---|---|---|
| 网络往返 | 8 次 | **1 次** |
| 模型推理 | 8 次 × 5–20s = **40–160s** | **0 次** |
| "该怎么做"判断 | 每次现想（不确定）| **查表（确定）** |
| **合计** | **★ 100–160 秒** | **★ 2–5 秒** |

**★★ "快"的三个来源**：
1. **省掉模型推理**（最大头，每步 5–20s → 0）
2. **省掉网络往返**（`script.exec` 一次跑完）
3. **省掉"判断"**（查表回放 vs 现场推理）→ **更重要的是【可预测】** ✓

## 六、★★★★★ 蜂群经验同步（用户 2026-09-19 提出，本节为设计）

> **用户原话**："我们既然是蜂群，我们每个手机学习到的经验和踩到的坑，
> 针对某个版本的技能卡等都是可以同步到 ai 服务端的，
> 对于意图类的命令，产出的经验都是集群可以复用的，对吗？"
>
> **答**：**对。而且这是蜂群架构【必须做】的一件事** ——
> 否则 22 台各学一遍 = 学费付 22 次，且经验发散、无法归并。

### 6.1 同步什么（四类资产，按复用价值排序）

| # | 资产 | 内容 | 复用价值 |
|---|---|---|---|
| **1** | **做法表 / 坑**（负样本）| "点了这个会弹广告"、"这页搜索是图标不是文字，`find_text` 找不到"、"滑动后要等 800ms" | **★ 最高** —— 让 21 台**不去踩同一个坑** |
| **2** | **技能卡**（正样本）| 意图 → `steps` 序列（`script.exec` 原生格式）| **高** —— 界面一致即可复用 |
| **3** | **页面表** | 页面签名 → 条件-动作（"抖音首页特征：底部 4 tab + 右上角搜索"）| **高** |
| **4** | **环境指纹** | App 版本 / 屏幕尺寸 / 语言 / 系统版本 | **必备元数据**（见 6.3①）|

**★★ 关键判断**：**"踩到的坑"比"成功经验"更值钱** ✓
—— 成功经验只告诉你能做什么；**坑能避免 21 台重复踩** ✓

### 6.2 怎么同步（三段）

```
【上报】设备完成一次执行（成功或失败）
    → 打包：{意图, steps/trace, 结果, 环境指纹, 设备指纹, 时间戳}
    → POST 到中心（AI 服务端或专用同步端点）

【中心处理】合并 / 去重 / 冲突检测 / 统计
    · 同一意图 + 同一环境指纹 → 归并
    · 记录【验证计数】（多少台、成功多少次、失败多少次）
    · 冲突（同意图不同 steps）→ 并存，按成功率排序
    · ★ 版本化（技能卡带版本号，可回滚）

【下发】设备拉取
    · 启动时 / 定期 / 执行失败时拉取
    · ★ 按【环境指纹】过滤（只拉适用的）
    · 本地合并（本地学的优先？还是中心的高计数优先？→ 见 6.3②）
```

### 6.3 ★ 三个必备护栏（否则"集群复用"会变成"集群一起坏"）

**① 环境指纹（技能卡标注适用环境）**
```
技能卡必须带：App 版本 · 屏幕尺寸 · 语言 · 系统版本
→ 拉取时过滤，避免"在 6s 上学的卡被下到 12 上"导致必然失败
```

**② 验证计数与来源可信度**
```
每张卡记录：在多少台设备上、成功多少次、失败多少次
→ 优先用【高计数 + 高成功率】的
→ 单台一次成功的卡，不急着全量
```

**③ ★ 灰度发布（防止失败放大）**
```
新卡 / 新版卡 → 先在【1–2 台】试跑
→ 成功率达标（如 ≥90%、≥N 次）才全量下发
→ 带版本号，可回滚
```

### 6.4 ★ 必须诚实指出的风险

| 风险 | 说明 | 护栏 |
|---|---|---|
| **失败放大** | 一条坏经验 → 22 台一起坏 | **灰度 + 回滚**（6.3③）|
| **行为同质化** | 全群走同一路径，平台反爬/风控易识别 | **做法表保留多条备选，运行时随机/轮换** |
| **技能库并发写** | 22 台同时上报 | 中心侧串行化 + 幂等（按 `{意图,环境,设备}` 去重）|
| **污染传播** | 某台设备环境异常产出的卡被当成通用 | **环境指纹过滤 + 来源标注** |
| **界面漂移** | App 更新导致全群同时失效 | **失效检测**（`expect` 断言失败即标记该卡失效，回落到①重学）|

## 七、★★ 基于本架构倒推的设计原则（用户说"可以基于此来倒推"）

**从四层结构倒推出的硬约束**：

| # | 倒推出的原则 | 依据 |
|---|---|---|
| **1** | **设备端必须有 MCP 层**（协议终结在手机，网关只转发）| ② 是 MCP 服务端 |
| **2** | **命令必须结构化**（不是自由文本）| ① 到 ② 之间是命令，不是人话 |
| **3** | **设备端必须有技能库**（本地存储 + 检索 + 版本）| ② 要"查表→命中即回放" |
| **4** | **`script.exec` 是技能卡的执行载体**（★ 已有）| ② 一次往返跑完整套 |
| **5** | **验证必须零模型**（`screen.hash` / `expect` / `vision.find_text`）| ④ 要能自证，不能回问 AI |
| **6** | **AI 服务地址必须可配**（不能硬编码）| ③ 可插拔 |
| **7** | **必须有 MCP 的"意图层工具"**（`open_app{name}` 这种）| ① 客户端不下发原子动作 |
| **8** | **必须有中心同步端点**（上报 / 拉取 / 灰度）| §六 蜂群共学 |
| **9** | **技能卡必须带环境指纹** | §六 6.3① |
| **10** | **网关在网络层只做转发**（跨网时当"邮局"）| ② 是真正的服务端 |

## 九、一句话总结

> **手机是自主主体，AI 是可插拔服务，电脑只是两个可选角色之一。**
>
